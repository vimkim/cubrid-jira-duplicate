# CBRD 중복 이슈 검사기 요구사항

- 상태: 초안 (2026-11-06)
- 관련 이슈: [CBRD-27978](http://jira.cubrid.org/browse/CBRD-27978)
- 근거: `docs/issue-brief.md`, `docs/evidence.md`, `scripts/`

이 문서는 PoC가 만족해야 할 조건을 정한다. 구현 방식은 정하지 않는다. 후보 추출과 판정 방식은 6장의 평가로 고른다.

## 1. 해결할 문제

CBRD 이슈는 2025년 660건이 생성되었고, 2026년에는 11월 6일까지 1,483건이 생성되었다. 최근 30일에만 399건이 생성되었다. 한 사람이 모든 새 이슈를 읽고 중복을 걸러내는 방식은 이 속도를 따라가지 못한다. 이슈를 쓰는 사람과 에이전트도 같은 문제가 이미 등록되었는지 확인할 수단이 JQL 텍스트 검색뿐이다.

`resolution = Duplicate`로 닫힌 이슈는 2023-2025년 생성분에서 해마다 17-21건이었고, 2026년 생성분에서는 59건이다. 2026년 생성분은 중복으로 닫히기까지 중앙값 5.5일이 걸렸고, 4건 중 1건은 28일 넘게 열려 있었다. 같은 결함이 다른 언어, 다른 증상, 다른 추상 수준으로 쓰이면 제목의 단어가 거의 겹치지 않는다. 예를 들어 CBRD-27636과 CBRD-27638은 원본 CBRD-27516이 생긴 지 2주 뒤 같은 날 등록되었고, core dump 위치로 제목을 써서 원인으로 제목을 쓴 원본과 단어가 겹치지 않는다.

지금 보고자가 할 수 있는 검색은 원본을 거의 찾지 못한다(`docs/evidence.md` 2절). 중복 이슈의 제목 단어를 그대로 `text ~`에 넣으면 원본이 상위 10위 안에 드는 쌍은 202쌍 중 18쌍(8.9%)이다. 쿼리의 85%는 결과가 0건이고, 2026년에 생성된 중복 70쌍은 하나도 찾지 못했다. 원인은 JIRA 7.7.1 검색의 동작에 있다.
- 여러 단어를 AND로 묶는다.
- 모든 단어가 한 필드 안에 있어야 맞는다.
- 한국어 조사를 분리하지 않아서 "중복"과 "중복이"가 서로 맞지 않는다.

같은 단어를 OR로 묶으면 recall@10이 51.0%로 오르지만, 두 제목 중 한쪽만 한글인 쌍은 OR 검색으로도 15.6%만 찾는다. 2026년 중복 쌍의 31.4%가 이런 쌍이다.

## 2. 사용자와 사용 흐름

| ID | 사용자 | 흐름 |
|---|---|---|
| U1 | 이슈를 등록하는 에이전트 | `cubrid-jira-issue-write` 스킬로 초안을 쓴 뒤, `cubrid-jira create` 직전에 검사를 실행한다. 판정에 `duplicate`가 있으면 등록을 멈추고 사람에게 후보를 보여준다. |
| U2 | 이슈를 쓰는 사람 | 초안 Markdown 파일이나 제목과 본문을 넣어 같은 검사를 CLI로 실행하고, 후보를 읽고 직접 판단한다. |
| U3 | 사후 검사를 돌리는 사람 | 마지막 실행 이후 새로 등록된 이슈를 모두 검사하고, 중복이나 관련 의심 목록을 받는다. JIRA 웹 화면이나 다른 경로로 등록된 이슈를 잡는 용도다. |

U3이 PoC에 들어간 이유는 등록 전 검사만으로는 대부분의 이슈를 거치지 못하기 때문이다. 최근 30일 이슈 399건 중 에이전트 이슈 템플릿(`AI-Generated Context`)을 쓴 이슈는 48건(12.0%)이다(`docs/evidence.md` 6절). 이 템플릿을 쓰지 않는 에이전트도 있으므로 이 값은 에이전트 작성 비율의 하한이다.

## 3. 범위

PoC에 넣는 것:

- 등록 전 검사(U1, U2)와 사후 검사(U3).
- CBRD 프로젝트 전체 이슈. 닫힌 이슈와 Sub-task를 포함한다.
- 제목, 설명, 댓글, 상태, resolution, 유형, 컴포넌트, 영향 버전, 수정 버전, 링크, 생성·수정 시각.
- 정답 쌍으로 정확도를 재는 평가 명령.

PoC에서 빼는 것:

- JIRA에 쓰는 동작. 링크, 댓글, 라벨을 자동으로 달지 않고, 등록을 막지도 않는다.
- 첨부 파일, 다른 JIRA 프로젝트, `jira.cubrid.com`.
- 서버, 웹 화면, JIRA 플러그인.
- Teams 등 메신저로 보고서 보내기(FR-7).
- `cubrid-jira create` 안에 검사를 넣는 통합(FR-10).
- JIRA DB 덤프. 공개 REST API로 전체를 받는다.

## 4. 기능 요구사항

**FR-1 입력.** 검사는 세 가지 입력을 받는다.
- 초안 Markdown 파일. `cubrid-jira-issue-write`가 만드는 형식을 그대로 읽는다.
- 표준 입력이나 인자로 받은 제목과 본문.
- 기존 이슈 키. 사후 검사와 평가에서 쓴다. 이때 그 이슈 자신과, 그 이슈보다 나중에 생성된 이슈는 결과에서 뺄 수 있어야 한다.

**FR-2 후보.** 검사는 관련 가능성이 높은 기존 이슈를 순위대로 돌려준다. 기본 개수는 10개이고 옵션으로 바꿀 수 있다.

**FR-3 판정.** 각 후보에 `duplicate`, `related`, `unrelated` 중 하나와 판정 근거를 붙인다.
- `duplicate`. 같은 결함이나 같은 요청이라서 하나를 해결하면 다른 하나도 닫힌다.
- `related`. 같은 기능 영역이나 같은 원인 계열이라서 링크할 가치가 있다. 회귀, 상위·하위 작업을 포함한다.
- `unrelated`. 위 둘에 해당하지 않는다.

근거는 초안과 후보에서 판정을 뒷받침하는 문장이나 식별자를 인용한다.

**FR-4 닫힌 이슈 표시.** 후보가 이미 해결된 이슈면 상태, resolution, 수정 버전을 함께 보여준다. 보고자는 이걸 보고 자기 빌드에 수정이 들어갔는지 확인한다.

**FR-5 출력.** 사람용 텍스트와 에이전트용 JSON을 모두 낸다. JSON은 최소한 다음을 담는다.
- 검사 입력의 요약과 검사 시각.
- 인덱스가 마지막으로 동기화된 시각.
- 후보마다 키, URL, 제목, 상태, resolution, 수정 버전, 순위, 판정, 근거.
- 전체 판정. 후보 중 `duplicate`가 하나라도 있으면 `duplicate`다.

**FR-6 종료 코드.** 에이전트가 출력을 해석하지 않고도 결과를 구분할 수 있게, 종료 코드로 "중복 없음", "중복 의심", "오류"를 구분한다.

**FR-7 사후 검사.** 마지막 실행 이후 생성된 이슈를 모두 검사하고, `duplicate`나 `related` 판정이 나온 이슈만 모은 보고서를 낸다. 실행 상태(마지막으로 검사한 시각)는 로컬에 저장하고, 같은 구간을 다시 돌려도 같은 결과를 낸다. 보고서는 파일과 표준 출력으로 낸다. 같은 구간에 새로 생성된 이슈끼리도 비교한다. 이 경우 두 이슈 중 나중에 생성된 이슈를 중복 후보로 보고한다. 최근 90일 새 이슈의 21.4%는 2건 이상이 같은 분에 생성되었고, 1분에 11건이 생성된 적도 있다(`docs/evidence.md` 5절).

처리량 목표는 한 번 실행에 새 이슈 100건이다. 최근 하루 최대 생성 수는 34건이고, 주당 생성 수는 W33-W41 평균 44건에서 W42-W44 평균 88건으로 늘었다.

Teams로 보고서를 보내는 기능은 PoC에 넣지 않는다. 팀의 Teams 봇(`cubrid-teams-dev2bot`)에는 외부에서 동적 메시지를 넘겨받는 CLI나 HTTP 입구가 없어서 봇 쪽에 새 코드가 필요하다(`src/cli.ts:100`, `src/announcements.ts:6-48`).

**FR-8 데이터 동기화.** 처음에 CBRD 전체를 받아 검사기 전용 로컬 인덱스를 만든다. `cubrid-jira`의 캐시는 쓰지 않는다. 그 캐시는 `search`로 연 이슈만 담고, 생성·수정 시각을 날짜까지만 저장하며, resolution 날짜를 저장하지 않는다(`cubrid-jira`의 `src/cubrid_jira/markdown.py:686-762`, `cli.py:507-537`). 검사할 때마다 마지막 동기화 이후 수정된 이슈만 받아 인덱스를 갱신한다. 동기화가 실패하면 검사는 기존 인덱스로 계속하고, 출력에 인덱스 시각과 실패 사실을 적는다.

**FR-9 평가 명령.** 정답 쌍(6장)으로 후보 단계와 판정 단계의 지표를 계산하는 명령을 둔다. 같은 인덱스와 같은 설정으로 다시 돌리면 같은 후보 순위를 낸다.

**FR-10 에이전트 등록 경로 연결.** 에이전트가 새 CBRD 이슈를 만드는 경로에서 `cubrid-jira create`보다 먼저 검사를 실행한다. 판정이 `duplicate`이면 등록하지 않고 사람에게 후보와 근거를 보여준다. `related`만 있으면 후보를 보여주고 등록은 계속할 수 있다.

현재 상태는 다음과 같다.
- `cubrid-jira create`에는 생성 전에 다른 검사를 끼울 hook이 없다(`src/cubrid_jira/cli.py:691-784`).
- 어떤 스킬도 `cubrid-jira create`를 부르지 않는다. `cubrid-jira-issue-write`는 기존 이슈의 설명만 올리고, 새 이슈 생성은 별도 흐름으로 둔다(`references/publication.md:23`).
- 그래서 지금은 에이전트가 CLI를 직접 불러 이슈를 만든다. CBRD-27978도 그렇게 만들어졌다.

PoC는 `cubrid-jira-issue-write`에 "새 이슈 생성 전 검사" 단계를 넣는다. 스킬 밖에서 CLI를 직접 부르는 에이전트까지 막으려면 `cubrid-jira create`가 검사를 부르게 해야 한다. 이 통합은 PoC 뒤에 정한다(7장 "도구 위치").

## 5. 비기능 요구사항

**NFR-1 응답 시간.** 후보 목록은 5초 안에, LLM 판정까지 포함한 결과는 60초 안에 낸다. PoC에서 실제 값을 재고 이 목표를 조정한다.

**NFR-2 인덱스 신선도.** 동기화가 성공한 검사는 검사 시작 시각까지 생성된 모든 CBRD 이슈를 비교 대상에 넣는다. 하루 한 번 갱신으로는 부족하다. 원본이 먼저 생성된 202쌍 중 39.6%는 원본 생성 후 1일 안에, 10%는 약 0.4시간 안에 중복이 등록되었다(`docs/evidence.md` 3절). 반대로 2026년 중복은 원본과의 시간 차 중앙값이 13.0일이고 최대 3,764일이므로, 오래된 이슈도 비교 대상에서 빼지 않는다.

**NFR-3 데이터 반출.** 등록 전 초안과 후보 이슈를 Anthropic API(Claude)로 보내는 것은 허용한다(사용자 결정, 2026-11-06). 그 밖의 외부 서비스로 초안을 보내지 않는다. 임베딩이 필요하면 로컬 모델을 쓰거나, 다른 외부 서비스를 쓰기 전에 따로 승인을 받는다.

**NFR-4 비용.** LLM 비용의 부담 방식은 사용자가 정했다(2026-11-06). 내부 결정이라 공개 문서에는 적지 않는다. 검사마다 사용한 입력·출력 토큰 수를 JSON 출력에 남겨서 검사 한 번의 비용을 계산할 수 있게 한다. API 키는 환경 변수나 설정 파일에서 읽고, 출력이나 로그에 쓰지 않는다.

**NFR-5 권한.** 읽기는 로그인 없이 공개 REST API로 한다. 검사기는 JIRA 계정이 필요 없다.

**NFR-6 실행 환경.** 개발 서버(Linux)의 터미널에서 실행한다. GUI나 브라우저를 띄우지 않는다.

**NFR-7 재현성.** 문서와 보고서의 모든 수치는 저장소의 스크립트로 다시 계산할 수 있다.

## 6. 평가와 합격 기준

**정답 쌍.** `data/gold-pairs.jsonl`의 312쌍이다. `resolution = Duplicate`로 닫힌 이슈 249건 중 233건에서 나왔고, `python3 -I scripts/build_gold.py`로 다시 만든다(`docs/evidence.md` 1절).

| 출처 | 쌍 | 후보가 먼저 생성 | 후보가 나중 생성 |
|---|---|---|---|
| Duplicate 링크 | 74 | 50 | 24 |
| Relates 링크 | 71 | 33 | 38 |
| 댓글 언급 | 167 | 119 | 48 |
| 합계 | 312 | 202 | 110 |

댓글 언급 쌍 중 댓글에 "중복"이나 "dup"이 있는 쌍은 44쌍뿐이다. 나머지는 원본보다 관련 이슈를 가리키는 경우가 많다. 그래서 `duplicate` 판정의 정답으로는 Duplicate 링크 쌍과 단서 있는 댓글 언급 쌍만 쓴다.

**평가 방법.**
- 정답 쌍의 중복 이슈를 질의로 쓴다. 질의에는 그 이슈의 제목과 설명만 넣고, 댓글과 링크는 넣지 않는다. 댓글과 링크에는 원본 키가 적혀 있어 정답이 새기 때문이다.
- 비교 대상은 질의 이슈보다 먼저 생성된 이슈로 제한한다. 비교 대상 이슈의 댓글도 질의 이슈보다 먼저 달린 것만 쓴다. 등록 시점의 상황을 흉내 내기 위해서다. 오늘의 데이터로 기준선을 잰 결과, OR 검색 상위 10위 적중 103건 중 6건은 중복 생성 뒤 원본에 달린 댓글에 중복 이슈 키가 있었다.
- 원본이 질의보다 나중에 생성된 110쌍은 사후 검사(FR-7) 평가에만 쓴다.
- 지표는 전체와 함께 출처별, 2026년 생성 중복, 제목 언어가 다른 쌍으로 나눠 보고한다. 각 값에 Wilson 95% 신뢰구간을 붙인다. Duplicate 링크 50쌍처럼 작은 부분집합은 구간 폭이 ±13%p 안팎이다.

**합격 기준(사용자 결정, 2026-11-06).**
- 후보 단계에서 원본이 먼저 생성된 202쌍의 recall@10이 0.8 이상이다. 관련 이슈를 찾는 것도 후보 단계의 목적이므로 세 출처를 모두 센다.
- `duplicate` 판정의 정밀도가 0.8 이상이다.

같은 202쌍에서 현재 검색(AND)은 0.089, JIRA OR 검색은 0.510이다.

**정밀도 측정.** 정답 쌍의 질의마다 나온 `duplicate` 판정을 모은다. 정답 원본이면 맞음으로 센다. 정답 원본이 아닌 후보에 `duplicate`가 붙으면 사람이 검수해서 실제 중복인지 정한다. 정답 쌍은 사람이 알아챈 중복만 담기 때문에, 검수 없이 오답으로 세면 정밀도가 실제보다 낮게 나온다.

**방식 선택.** 현재 검색(AND)과 JIRA OR 검색을 기준선으로 두고, 어휘 검색, 다국어 임베딩, 둘의 결합을 recall@10으로 비교한다. 제목 언어가 다른 쌍의 recall@10을 따로 비교한다. 판정 단계는 후보 단계의 recall@10을 확인한 뒤 정밀도로 평가한다.

## 7. 결정 기록

## 8. 위험과 미결 질문

- 정답 쌍은 사람이 알아채고 Duplicate로 닫은 중복만 담는다. 아무도 알아채지 못한 중복은 평가에 없다.
- 일부 링크와 댓글은 로그인해야 보인다. 로그인 없이 보이는 원본 지시 이슈는 233건이고, 로그인하면 237건이다.
- 설명은 등록 후에 수정될 수 있다. 평가에 쓰는 설명이 등록 시점의 설명과 다르면 정답이 새거나 질의가 실제보다 좋아질 수 있다.
- 검사 한 번의 LLM 비용은 PoC에서 재기 전에는 모른다.
