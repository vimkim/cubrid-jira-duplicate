# 후보 검색 방식 비교

작성일 2026-11-09. `cubrid-jira-dup candidate-find`의 검색 방식을 어떻게 골랐는지 적는다. 사용법과 지금 방식의 수치는 [README](../README.md)의 "후보 찾기"에 있다.

## 결론

BM25와 다국어 임베딩(multilingual-e5-small)을 직접 결합한 방식을 골랐다. LanceDB와 Meilisearch는 같은 입력에서 recall이 더 낮았다. BGE Reranker v2 M3는 recall을 오히려 낮췄고 질의마다 수십 초가 걸렸다. 고른 방식은 평가용(test) recall@10이 전체 0.825, 2026년 생성 질의 0.800이라 두 합격 기준을 넘는다. 2026년 쪽은 35쌍 중 28쌍으로 기준선에 걸려 있어서, 한 쌍만 놓쳐도 기준 아래다.

## 비교 조건

모든 방식이 같은 입력을 썼다.

- 2026-11-09에 고정한 스냅샷. 익명으로 보이는 CBRD 이슈 7,968건이고, `issues` 데이터의 sha256 앞자리는 `4915010537b5`다.
- 검색 단위는 이슈마다 본문 행 하나(제목과 설명)와 댓글마다 행 하나다. 상태, resolution, 링크, 수정 버전은 색인과 점수에 넣지 않았다.
- 질의는 중복 이슈의 제목과 설명이다. 질의 이슈보다 먼저 생성된 이슈와, 그 시각 이전에 쓰고 고친 댓글만 검색했다(요구사항 7.2).
- 정답은 연결 후보가 먼저 생성된 202쌍이다. 조정용(dev) 99쌍으로 방식과 설정을 고르고, 평가용(test) 103쌍으로 합격을 판정했다(요구사항 7.3).
- 같은 임베딩 벡터를 모든 방식에 넣었다. 그래서 방식 사이의 차이는 어휘 검색과 결합 방식에서 나온다.

비교 단계의 마스킹은 `CBRD-<숫자>`만 가렸다. 최종 방식의 값은 `cbrd_27516`처럼 이슈 번호를 담은 식별자까지 가린 값이다. 두 마스킹에서 최종 방식의 recall 수치는 같았다.

## 비교표

recall은 recall@10 / recall@20이다. 각 방식의 행은 그 방식 안에서 dev 값으로 고른 설정이다.

| 방식 | dev | test | test 2026 | 전체 202쌍 | 서버 | 설치 크기 |
|---|---|---|---|---|---|---|
| JQL AND (제목 단어 그대로) | - | 0.097 / 0.097 | 0.000 / 0.000 | 0.089 / - | JIRA | - |
| JQL OR | - | 0.553 / 0.602 | 0.457 / 0.543 | 0.510 / - | JIRA | - |
| BM25만 (bm25s) | 0.556 / 0.626 | 0.680 / 0.728 | 0.800 / 0.800 | 0.619 / 0.678 | 없음 | bm25s |
| Meilisearch 1.56.1 하이브리드 | 0.566 / 0.626 | 0.689 / 0.699 | 0.657 / 0.686 | 0.629 / 0.663 | 필요 | 바이너리 356 MB |
| LanceDB 0.41 하이브리드 | 0.596 / 0.646 | 0.689 / 0.748 | 0.771 / 0.857 | 0.644 / 0.698 | 없음 | 419 MB |
| LanceDB + BGE Reranker v2 M3 (int8, 상위 50) | 0.455 / - | 0.505 / - | - | - | 없음 | 모델 545 MB 추가 |
| **고른 방식** | 0.737 / 0.788 | 0.825 / 0.835 | 0.800 / 0.829 | 0.782 / 0.812 | 없음 | 설치 207 MB, 모델 465 MB |

JQL 기준선은 제목만으로 오늘의 JIRA를 검색한 값이고, 7.2의 시간 제한을 적용하지 않았다(`docs/evidence.md` 2절). 위 표의 다른 방식은 모두 시간 제한을 적용했다.

방식별로 확인한 사실은 다음과 같다.

- **Meilisearch.** 질의의 앞 10단어만 검색에 쓴다. 위치 1-41에 무의미한 단어를 넣어 확인했고, 11번째부터는 무시되었다. 설명이 수천 자인 초안에는 맞지 않는다. 키워드 점수에 단어 빈도와 문서 길이 가중이 없어서, 한 질의에서 687개 행이 같은 점수로 묶였다. 한국어는 사전 기반으로 조사를 떼어 `중복이 발생한다`가 `중복`과 맞는다. 하지만 `테이블의`는 한 토큰으로 남아 `테이블`과 맞지 않는다. 내장 임베더는 CPU에서 돌지만, 본문 7,968행 색인에 2,539초가 걸렸다. GitHub 릴리스 바이너리는 내려받기가 504로 실패했고, 조사로는 GLIBC 2.35가 필요해 이 서버(2.34)에서 돌지 않을 것으로 보였다(실행해 보지는 못했다). 그래서 공식 컨테이너 이미지의 musl 바이너리를 꺼내 root 없이 실행했다. 노트북 사용자는 서버 프로세스를 따로 띄워야 한다.
- **LanceDB.** 서버 없이 파이썬 안에서 돈다. 기본 토크나이저는 한국어 어절을 그대로 둬서 `종료`가 `종료됩니다`와 맞지 않는다. 한국어 형태소 사전(lindera ko-dic)은 들어 있지 않다. Rust로 CLI를 빌드하고 48 MB 사전을 받아 컴파일해야 쓸 수 있고, 써도 recall이 오르지 않았다. 행에서 이슈로 묶는 기능이 없어 행을 넉넉히 받아 직접 묶었다.
- **BGE Reranker v2 M3.** 상위 50개를 다시 매기자 recall이 떨어졌다. 정답 쌍은 공통 함수 이름이나 스택 한 줄로 이어지는 경우가 많다. 그런데 이 모델은 주제의 비슷함을 보고, 512 토큰에서 잘린 뒤의 스택은 보지 못한다. 50쌍을 다시 매기는 데 int8로 질의당 16.8초(16스레드)와 44.6초(4코어)가 걸렸다.
- **BGE-M3 임베딩.** 이 서버의 40코어 상한에서 3시간 50분(68 CPU-시간) 동안 코퍼스를 다 임베딩하지 못해서 중단했다. recall은 재지 못했다. 처음 한 번의 색인만으로도 노트북에 맞지 않는다.

## 고른 방식이 이긴 이유

BM25, 임베딩, 제목 검색을 따로 순위 매겨 합친 것만으로는 dev recall@10이 0.636이었다. 두 가지가 더해져서 0.737이 되었다.

- **생성 시각 근접도.** 정답 쌍에서 연결 후보의 44%는 질의보다 1일 안에, 71%는 30일 안에 먼저 생성되었다. 임의의 이슈라면 각각 0.3%와 4%다. 질의 시각에 가까운 이슈에 작은 가산점을 주자 dev recall@10이 0.636에서 0.697로 올랐다. 이 신호는 생성 시각만 쓰고 링크나 상태는 쓰지 않는다. 대가로 오래된 이슈의 진짜 중복은 순위가 밀린다.
- **콜 스택 함수.** 질의의 스택 맨 위 함수 두 개로 따로 BM25 검색을 했다. 코어 덤프 보고는 같은 함수 이름을 공유하지만, 긴 로그 안에서는 그 이름이 묻힌다. 이 채널을 넣자 dev recall@10이 0.697에서 0.737로 올랐고, test는 그대로였다.

dev에서 효과가 없던 시도는 다음과 같다. 한국어 형태소 분석(kiwipiepy), 다른 임베딩 모델(MiniLM, potion)을 채널로 더하기, 질의 확장(RM3, Rocchio), 템플릿 절 고르기, 학습한 결합(로지스틱 회귀, 질의 단위 교차검증), 긴 설명을 조각으로 나눈 임베딩이다. 학습한 결합은 손으로 정한 가중치와 거의 같은 가중치를 찾았다.

## recall의 상한

고른 방식이 놓친 48쌍을 사람이 읽고 나눴다(스냅샷, `CBRD-<숫자>` 마스킹).

| 분류 | 쌍 |
|---|---|
| 같은 문제이고 공통 텍스트가 강한데 순위가 낮다 | 8 |
| 같은 문제를 다르게 표현했거나 다른 언어로 썼다 | 9 |
| 관련은 있지만 다른 문제다(회귀의 원인, 수정 하위 작업, 후속 기능 등) | 28 |
| 텍스트에서 연결이 보이지 않는다 | 3 |

같은 문제인 17쌍을 모두 찾아도 전체 recall@10은 약 0.85, dev는 약 0.80이다. 같은 문제인 쌍만 세면 고른 방식은 이미 171쌍 중 154쌍(0.90)을 찾는다. 요구사항 7.4는 관련 이슈를 찾는 것도 후보 단계의 목적으로 보고 세 출처를 모두 센다. 그래서 남은 실패의 대부분은 텍스트 검색으로 줄일 수 없다.

두 제목 중 한쪽에만 한글이 있는 32쌍은 recall@10이 0.469로 가장 약하다. 이 쌍을 잇는 것은 의미이지 공통 단어가 아니다. 더 강한 다국어 모델이 필요하지만, 시험한 큰 모델(BGE-M3)은 노트북에서 색인을 만들 수 없었다.

## 노트북 조건의 속도

이 서버의 CPU 4개에 고정해서 쟀다. 노트북 CPU와 같지 않으므로 대략의 값이다.

- 3,000자 초안 한 건은 동기화를 포함해 3.82초(중앙값, 10회, 범위 3.70-5.28초)가 걸렸다. CPU 40개에서도 3.82초였다. 시간의 대부분(2.4초)은 새 프로세스가 임베딩 모델을 올리는 데 쓰고, 이 작업은 코어 수와 상관이 없다.
- 처음 색인을 만들 때의 임베딩은 4코어에서 약 30-33분으로 추정한다. 길이 순으로 고른 10% 표본이 178-198초 걸린 값의 10배다. 16스레드에서는 같은 표본이 68-74초였고, 실제 전체 임베딩은 771초였다. 최대 메모리는 약 1.5 GB다.

## 다시 재는 법

고른 방식의 수치는 저장소의 명령으로 다시 잰다.

```bash
cubrid-jira-dup sync
cubrid-jira-dup eval candidates --method hybrid
```

LanceDB, Meilisearch, 리랭커, 여러 변형을 비교한 스크립트는 일회용 실험이라 저장소에 넣지 않았다. 이 문서의 해당 수치는 그 실험의 기록이다.
