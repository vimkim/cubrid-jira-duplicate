# CBRD 이슈 작성 브리프: JIRA 이슈 등록 전 중복·유사 이슈 탐지

작성일 2026-11-06. 이 파일은 새 이슈를 작성할 에이전트에게 주는 작업 지시와 근거다.

## 사용자 목표

CBRD 이슈 생성 속도가 빨라져서, 한 사람이 새 이슈를 모두 읽고 중복을 걸러내는 방식이 더는 통하지 않는다. 사용자는 에이전트(`cubrid-jira` 스킬과 CLI)나 사람이 이슈를 등록하기 직전에, 관련된 이슈가 jira.cubrid.org에 이미 있는지 알려주는 도구를 만들려고 한다. 이번 작업의 결과물은 그 도구가 필요한 이유를 설명하는 CBRD 이슈 초안이다. 도구 구현이나 설계 확정은 이번 범위가 아니다.

## 할 일

1. 이 파일 전체를 읽는다.
2. `cubrid-jira-issue-write` 스킬을 Skill 도구로 불러서 그 절차대로 한국어 이슈 초안을 쓴다. 아직 이슈 키가 없으므로 스킬의 publication 참조 문서가 말하는 ticket-free 초안(`issues/<descriptive-slug>.md`)으로 `/home/vimkim/gh/my-cubrid-jira`에 저장한다. 스킬이 정한 Document Git workflow와 작업 체크아웃 규칙을 따른다.
3. 본문의 숫자는 아래 명령을 다시 실행해서 나온 최신 값으로 쓴다. 이 스크립트는 공개 REST API를 익명으로 읽는다.

   ```bash
   python3 -I /home/vimkim/gh/cubrid-jira-duplicate/scripts/measure_cbrd.py
   ```

   이슈 본문에는 개인 도구 대신 누구나 실행할 수 있는 근거를 쓴다. 예를 들면 JQL 문자열이나 `http://jira.cubrid.org/rest/api/2/search` 호출이다.
4. 스킬의 리뷰 기준과 링크 검사를 통과시키고, 작업 체크아웃에 로컬 커밋까지 만든다.
5. 이슈 유형을 스킬의 분류 참조 문서로 정하고 이유를 한 줄로 적는다. 그다음 아래 명령을 `--yes` 없이 dry-run으로 실행한다.

   ```bash
   cubrid-jira create --project CBRD --type "<추천 유형>" --summary "<제목>" \
     --description-file <초안 절대 경로> --from markdown --output json
   ```

6. 여기서 멈추고 한국어로 보고한다. 보고에는 초안 절대 경로, 작업 브랜치와 커밋, 추천 유형과 이유, 제목과 한 줄 요약, dry-run 결과의 요점, 남은 결정 사항을 넣는다.

## 하지 말 것

- `--yes`를 붙인 명령, `git push`, 그 밖에 JIRA나 원격 저장소에 쓰는 동작은 하지 않는다. 사용자가 초안과 dry-run을 본 뒤 따로 승인한다.
- CBRD는 로그인 없이 누구나 읽는 공개 프로젝트다. 본문에 회사 내부의 검토 체계, 비용, API 키, 계정, 고객사 이름을 쓰지 않는다.
- 구현 방식을 확정된 것처럼 쓰지 않는다. `이슈 수행 방안`은 스킬 기본값(TBD)을 쓴다. 아래 "제안 방향"은 ANALYSIS 후보로만 다룬다.

## 문제 (사용자 보고)

- 이슈가 빠르게 늘어서 등록된 이슈를 한 사람이 모두 읽고 중복을 판단하기 어려워졌다.
- 버그를 발견한 사람은 같은 문제가 이미 등록되었는지 확인하기 어렵다. 그래서 같은 문제가 여러 이슈로 따로 올라온다.
- 에이전트가 `cubrid-jira create`로 이슈를 등록하는 경우가 늘고 있다. 에이전트도 등록 전에 기존 이슈를 확인할 수단이 없다.

## 필요한 결과

- 이슈를 등록하기 직전에 초안과 관련된 기존 CBRD 이슈 후보와 판정(중복, 관련, 무관)을 볼 수 있어야 한다.
- 사람과 에이전트가 같은 검사를 쓸 수 있어야 한다.
- 검사가 얼마나 맞는지 숫자로 보여줄 수 있어야 한다. Duplicate로 닫힌 이슈와 그 원본의 쌍이 그 기준이 될 수 있다.

## 제안 방향 (ANALYSIS 후보, 확정 아님)

사용자와의 요구사항 인터뷰에서 나온 권고안이다. 사용자는 아직 각 항목을 승인하지 않았다.

- 사용 시점은 등록 전 검사부터 시작한다. 웹 UI로 이미 등록된 이슈를 사후에 훑는 탐지는 다음 단계로 둔다.
- 검사 결과는 참고용이다. JIRA에 아무것도 쓰지 않고 등록을 막지도 않는다. 에이전트 흐름에서는 중복 판정이 나오면 등록을 멈추고 사람에게 후보를 보여준다.
- 판정은 duplicate, related, unrelated 세 단계로 나눈다. 이미 Fixed로 닫힌 이슈와 증상이 같으면 Fix Version을 함께 보여준다.
- 데이터는 CBRD 전체를 쓴다. 닫힌 이슈와 Sub-task를 넣고, 첨부 파일과 다른 프로젝트는 뺀다. 공개 REST API로 충분하므로 JIRA DB 덤프는 PoC에 필요 없다.
- 후보 추출은 어휘 검색(BM25 등)과 다국어 임베딩을 함께 쓰고, 상위 후보를 LLM이 읽고 판정하는 방식이 후보다. 어떤 방식을 쓸지는 위 정답 쌍으로 측정해서 고른다.

## ANALYSIS에서 정할 질문

- 웹 UI로 직접 등록되는 이슈의 비율은 얼마인가. 이 비율이 높으면 사후 탐지를 앞당겨야 한다.
- 성공 기준치는 무엇인가. 예를 들면 원본이 상위 10개 후보에 드는 비율, 중복 판정의 정밀도다.
- 등록 전 초안에는 공개되지 않은 정보가 있을 수 있다. 그런 초안을 외부 LLM 서비스로 보낼 때의 방침은 무엇인가.
- 도구를 CLI로 둘지 서버로 둘지, `cubrid-jira`에 어떻게 연결할지.
- 인덱스를 얼마나 최신으로 유지해야 하고, 검사 한 번에 시간을 얼마까지 쓸 수 있는지.
