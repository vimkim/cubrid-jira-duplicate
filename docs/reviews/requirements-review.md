# CBRD 중복 이슈 검사기 요구사항 리뷰

2026-11-06. 검토 기준은 `docs/requirements` 브랜치의 `aafe0801b5142fecfc3364d3d89073c37f2e5107`이다.

현재 요구사항만으로는 같은 PoC를 구현해 같은 합격 판정을 내리기 어렵다. 평가 입력에 정답이 남을 수 있고, 사후 검사의 시간 순서와 재시도 규칙, 에이전트의 오류 처리가 확정되지 않았다.

발견 사항은 심각도 순으로 High 6건, Medium 10건, Low 1건이다. High는 합격 판정을 무효로 만들거나 이슈 누락·잘못된 등록 진행을 일으키는 문제다. Medium은 구현 또는 검증 결과가 달라지는 계약의 빈칸이다. Low는 독해와 용어 문제다.

검토 대상은 [요구사항](../requirements.md), [이슈 브리프](../issue-brief.md), [측정 근거](../evidence.md), `scripts/`의 Python 파일 7개, `data/gold-pairs.jsonl`, `data/baseline-results.jsonl`이다. [CBRD-27978](http://jira.cubrid.org/browse/CBRD-27978)의 제목과 설명도 익명 GET으로 확인했다. 이슈의 ANALYSIS 후보 중 등록 전 검사만 먼저 하자는 과거 제안은 이번 사용자 결정을 대체하지 않는다.

검토 중 다른 작업에서 `docs/evidence.md`와 `scripts/measure_volume.py`를 수정했다. 추가된 월별 측정과 사용자 확인 사항도 읽었으며, 템플릿 해석에 관한 15번에 반영했다. 두 파일은 수정하지 않았다. 검토 대상 `docs/requirements.md`는 기준 커밋과 같다.

등록 전·후 검사를 모두 PoC에 넣는 결정, Anthropic API를 사용하는 허용 범위, recall@10 ≥ 0.8과 `duplicate` 정밀도 ≥ 0.8은 유지한다. 아래 수정안의 추가 검증 조건은 이 숫자를 바꾸자는 제안이 아니다.

## 1. [High] 평가의 시간 제한이 제목·설명·링크와 댓글 수정 이력까지 적용되지 않는다

- 위치: 6장 평가 방법, FR-8, 8장 설명 수정 위험. 요구사항 125, 126, 165행.
- 문제: 질의에서 댓글과 링크를 빼고 후보 댓글의 생성 시각만 제한해도 정답 누수는 남는다. 질의와 후보의 현재 제목·설명에 사후 분석이 들어갈 수 있다. 후보의 현재 링크, resolution, 수정 버전도 미래 정보다. 일찍 작성한 댓글을 나중에 고친 경우에는 댓글 `created` 필터를 통과한다. 현재 내용으로 만든 검색 인덱스에서 결과만 나중에 걸러도 후보 순위에 이미 미래 정보가 반영된다.
- 근거: 근거 문서 2.5절의 기준선은 오늘의 인덱스다. 저장된 OR 적중 103쌍 중 6쌍에는 질의 생성 후 후보에 추가된 역참조 댓글이 있다. 재계산도 6/103이다. 이는 특정 단서의 관측 수이며 전체 누수의 상한이 아니다. 원문 캐시의 CBRD-27044 설명에는 정답 후보 CBRD-24794 키가 직접 들어 있다. 이 사례만으로 사후 편집을 증명할 수는 없지만, 현재 규칙이 설명 속 정답 키를 허용함은 확인된다. 8장은 설명 편집 위험을 적고도 평가 처리 규칙을 주지 않는다.
- 수정안: 평가 프로필과 필드별 허용 규칙을 정한다. 역사 재현 프로필은 질의 등록 시각의 질의 제목·설명과 그 시각 이전에 존재한 후보 필드만 사용하고, 댓글은 생성·수정 시각을 모두 검사한다. 이력 복원이 안 되는 필드는 복원된 것처럼 사용하지 않는다. 정제는 검색 인덱스 생성 전과 판정 입력 생성 전에 동일하게 적용한다. 정답 쌍과 provenance는 평가기만 읽는다.
- 합격 조건: 미래 댓글, 일찍 생성했지만 나중에 편집한 댓글, 사후 설명, 정답 링크를 각각 넣은 검증 자료에서 해당 정보가 검색·판정 입력에 들어가지 않음을 확인한다. 공개 이력으로 202쌍 전체를 복원할 수 없다면, 전체에 적용할 고정된 현재 스냅샷과 정답 단서 제거 규칙을 별도 프로필로 명시한다. 그 점수를 역사 재현 성능으로 부르지 않는다. 역사 재현 가능한 부분집합의 수와 성능도 따로 보고한다. 분모를 조용히 줄여 합격시키지 않는다.

## 2. [High] 댓글에 중복 단어가 있다는 사실을 쌍의 중복 정답으로 취급한다

- 위치: 6장 정답 쌍·정밀도 측정, 7장 정답 쌍 결정, FR-3.
- 문제: `comment_dup_cue=true`는 언급된 후보가 중복 원본임을 보장하지 않는다. 그런데 이 집합을 정밀도의 자동 정답으로 쓰므로 실제로 `related`여야 할 예측을 정답으로 셀 수 있다. 정답 밖의 예측만 사람이 검수하는 절차로는 이 오류를 잡지 못한다.
- 근거: `scripts/build_gold.py` 51, 52, 56행은 댓글 전체의 `중복|dup` 여부를 댓글에 나온 모든 CBRD 키에 붙인다. 캐시의 CBRD-21113 댓글은 CBRD-21103 수정 후 테스트가 다시 실패해 새 이슈 CBRD-21118을 열었다고 설명한다. 두 쌍 모두 `comment_mention`, `comment_dup_cue=true`다. CBRD-21118은 FR-3이 `related`에 포함한 회귀 사례인데도 현재 규칙상 `duplicate`의 정답 후보에 들어간다. 근거 문서 1절도 링크 방향을 원본 판별 근거로 신뢰할 수 없다고 경고한다.
- 수정안: provenance와 사람이 확정한 관계 라벨을 분리한다. 자동 추출한 키·중복 단어는 검수 후보를 만드는 근거로만 쓴다. 정밀도에 사용할 양성 쌍은 Duplicate 링크 쌍을 포함해 FR-3 기준으로 검수하고, 라벨·검수 근거·판정 불가 여부를 저장한다. 관련 이슈 검색용 202쌍과 중복 판정용 라벨 집합을 구분한다.
- 합격 조건: CBRD-21113의 두 참조처럼 중복 원본과 회귀 이슈를 한 댓글에서 언급하는 자료에 서로 다른 관계 라벨이 붙는다. 확정하지 못한 쌍은 자동 정답으로 세지 않고 미확정 수를 보고한다.

## 3. [High] 정밀도가 중복 이슈만 있는 질의 집합에서 측정되고, 무응답 전략도 합격할 수 있다

- 위치: 6장 합격 기준·정밀도 측정·방식 선택, 8장 표본 편향.
- 문제: 사람이 이미 Duplicate로 닫은 이슈만 질의로 쓰면 실제 신규 초안의 중복 비율을 반영하지 못한다. 새로 예측한 양성의 사람 검수는 라벨 누락을 보완하지만 질의 선택 편향은 없애지 못한다. 같은 202쌍으로 방식을 선택하고 합격도 판정하면 평가 자료에 맞춘 선택이 된다. `duplicate`를 전혀 내지 않을 때의 0/0 처리와 예측 한두 건만 낼 때의 판정 검출률도 없다.
- 근거: 202쌍은 중복 이슈 160건에서 나오며, 312쌍 전체도 Duplicate로 닫힌 233건만 포함한다. 근거 문서 7절과 요구사항 163행이 미발견 중복의 부재를 인정한다. 후보 검색의 recall이 높아도 판정기가 거의 전부 `related`로 내면 실제 등록 중단에 도움이 되는지는 알 수 없다.
- 수정안: 기존 202쌍의 후보 recall 게이트를 유지한다. 판정 정밀도는 별도로 고정한 연속 신규 이슈 표본이나 신규 초안 표본에서도 측정한다. 중복이 없는 이슈와 관련만 있는 이슈를 포함하고, 표본 선정 규칙·기간·최소 검수량을 실행 전에 고정한다. 예측과 기존 provenance를 보지 않고 관계를 검수하는 절차와 이견 해결 규칙을 둔다. 조정용 자료와 최종 평가 자료는 같은 이슈 또는 같은 결함의 쌍이 양쪽에 걸치지 않게 나눈다. 전체 202쌍을 최종 게이트로 쓰려면 그 라벨로 설정을 조정하지 않는다.
- 합격 조건: `precision = TP / (TP + FP)`의 TP·FP·미확정 수를 함께 출력한다. 예측 양성이 0건이면 정밀도를 합격으로 처리하지 않는다. 최소 검수량 미달은 평가 불충분이다. 검수 가능한 양성 중 몇 건을 `duplicate`로 찾았는지와 질의당 오탐도 보고한다. 0.8은 점추정치 기준인지 신뢰구간 하한 기준인지 명시한다. 사용자 결정에 맞는 기본 해석은 점추정치 ≥ 0.8이다.

## 4. [High] 사후 검사에서 질의·후보의 방향과 동시 생성 처리가 정해지지 않았다

- 위치: FR-1, FR-7, 6장 사후 평가, 7장 정답 쌍 결정.
- 문제: FR-1은 나중 이슈를 제외하는 옵션을 제공하고, FR-7은 같은 구간에서 나중에 생긴 이슈를 "중복 후보"로 보고한다. 6장은 기존 중복 이슈를 질의로 쓰면서 나중 후보 110쌍을 사후 평가로 보낸다. 오래된 질의만 검사하면 나중 대표 이슈를 놓치고, 나중 이슈를 질의로 삼으면 저장된 정답 쌍의 방향과 반대가 된다. 생성 시각이 같은 경우와 같은 쌍의 중복 보고도 정의되지 않았다. 사후 검사에는 별도의 관측 가능한 합격 조건도 없다.
- 근거: 정답 파일에는 CBRD-23362와 CBRD-23361의 `created`가 모두 `2019-09-29T19:11:38.000+0900`인 쌍이 있다. `candidate_before_duplicate=false`를 전부 나중 생성으로 세어서 실제 구성은 먼저 202쌍, 나중 109쌍, 동시 1쌍이다. CBRD-27565와 CBRD-27566은 양방향 정답 행도 있다. 근거 문서 5절은 같은 분 생성 164/768건과 1분 최대 11건을 확인한다.
- 수정안: 사후 검사에서 새 이슈를 질의로 삼고 자기 자신을 항상 제외한다. 실행 구간의 새 이슈 전체가 서로 검색 가능하도록 한 뒤 검사한다. 쌍의 식별자는 방향 없는 두 키로 정하고, 출력에는 `query_key`, `candidate_key`, 생성 순서를 별도로 둔다. 생성 순서는 중복 관계나 대표 이슈 선택을 결정하지 않는다. 동시 생성 정렬에는 키 번호 같은 명시적 보조 기준을 쓴다. 110쌍은 "나중 또는 동시 후보"로 고쳐 세고 평가 시 필요한 방향으로 변환한다.
- 합격 조건: 기존 이슈와 새 이슈, 같은 실행 구간의 새 이슈 두 건, 생성 시각이 같은 두 건을 각각 검사한다. 검수된 정답 쌍이 설정된 후보 범위에 있고 판정 가능한 자료라면 해당 쌍을 보고하며 자기 자신이나 동일 쌍을 중복 보고하지 않는다. 110쌍의 사후 후보 recall과 판정 정밀도를 별도로 보고하고, 202쌍만 통과한 결과를 사후 검사 검증 완료로 부르지 않는다. 사후 프로필에도 후보 recall@10 ≥ 0.8과 `duplicate` 정밀도 ≥ 0.8을 각각 적용하는 것을 제안한다.

## 5. [High] 실행 시각 하나만 저장하면 부분 실패와 경계 시각에서 이슈가 누락된다

- 위치: U3, FR-7, FR-8, NFR-2, 7장 처리량.
- 문제: "마지막 실행 이후"가 실행 시작·종료·완료한 이슈의 생성 시각 중 무엇인지 불명확하다. 최초 실행 범위, 분 단위 JQL 경계, 페이지 조회 중 새로 생긴 이슈, 실패한 이슈, 100건 초과분의 처리도 없다. 보고서 저장 전에 체크포인트를 옮기거나 기존 인덱스로 검사한 실행을 완료로 기록하면 다음 실행에서 빠진 이슈를 다시 검사하지 않을 수 있다.
- 근거: 근거 문서 2.2절의 같은 분 생성 3쌍은 분 단위 JQL 필터가 초 단위 순서를 대체하지 못함을 보여 준다. FR-8은 동기화 실패 후 계속 실행하도록 한다. FR-7은 100건을 처리할 목표만 제시하고 101건부터의 동작을 정의하지 않는다.
- 수정안: 구간을 명시적인 시작 시각과 실행 시작 시 고정한 종료 시각으로 표현하고, 익명 JQL 시간대 +0900과 경계 포함 규칙을 정한다. 분 단위보다 넓게 조회한 뒤 원문 타임스탬프로 구간을 판별하고 키로 중복을 제거한다. 최초 실행에는 시작 시각을 요구하거나 명시한 기본 범위를 사용한다. 100건은 처리 능력 검증 표본으로 두고 백로그를 조용히 자르는 제한으로 쓰지 않는다. 페이지나 실행으로 나눌 경우 미처리 구간을 남긴다. 결과 파일을 안전하게 저장하고 모든 대상의 성공 또는 재시도 대상을 기록한 뒤에만 완료 체크포인트를 전진시킨다. 검색에 늦게 나타나는 이슈를 재조회하는 규칙도 둔다.
- 합격 조건: 0건·100건·101건, 분 경계 양쪽의 이슈, 페이지 중간 실패, 판정 중간 실패, 보고서 저장 실패, 체크포인트 기록 직전 종료를 재현한다. 재실행 후 대상 키 집합이 기대 집합과 같고 보고된 쌍이 중복되지 않아야 한다. 동기화 실패 실행은 완전 검사로 기록하지 않는다.

## 6. [High] 종료 코드와 불완전 결과에 대한 에이전트 동작이 없다

- 위치: U1, FR-5, FR-6, FR-8, FR-10, 3장 제외 범위, 7장 결과의 효력.
- 문제: FR-6은 코드의 뜻만 나열하고 숫자와 우선순위를 주지 않는다. `related`만 있거나 동기화에 실패한 경우, LLM 판정이 일부 실패한 경우의 코드가 없다. 에이전트가 오류를 중복 없음으로 받아들이면 미검사 등록이 진행된다. U1·FR-10의 등록 중단과 3장·7장의 "등록을 막지 않는다"도 행위 주체를 구분하지 않아 서로 다른 정책으로 구현될 수 있다.

## 수치 감사

다음 명령은 파일을 쓰지 않고 정답의 시간 구분과 기준선 핵심 숫자를 다시 확인한다.

```bash
python3 -B -I - <<'PY'
import collections
import json
from datetime import datetime
from pathlib import Path

def read_rows(path):
	return [json.loads(line) for line in Path(path).read_text().splitlines()]

pairs = read_rows('data/gold-pairs.jsonl')
rows = read_rows('data/baseline-results.jsonl')
def ordering(pair):
	left = datetime.fromisoformat(pair['candidate_created'])
	right = datetime.fromisoformat(pair['duplicate_created'])
	return 'earlier' if left < right else 'later' if left > right else 'equal'

print('time ordering', dict(collections.Counter(map(ordering, pairs))))
for variant in ('and', 'or'):
	subset = [row for row in rows if row['variant'] == variant]
	queries = {row['duplicate']: row for row in subset}
	print(variant, 'pairs', len(subset), 'queries', len(queries),
		'top10', sum(row['in_top10'] for row in subset),
		'zero', sum(row['total_hits'] == 0 for row in queries.values()))
PY
```

기대 출력의 핵심 값은 시간 구분 `earlier=202, later=109, equal=1`, AND `202쌍, 160질의, top10=18, zero=136`, OR `202쌍, 160질의, top10=103, zero=0`이다.
